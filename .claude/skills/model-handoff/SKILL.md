# 模型间任务交接

主会话：当前对话里负责设计和验收的 agent。外包：用户指定的另一个模型会话，默认 Grok。

主会话不能直接调用外包，这是人在环交接：主会话写提示词 → 用户拿到外包会话里跑，结果写进仓库 → 用户说「跑完了」→ 主会话验收后继续开发。不要设计或暗示「主会话自动调用外包」的流程。

## 1. 先判断该不该外包

给出一句裁决（✅ 适合外包 / ❌ 自己做）和理由。

适合外包，四条尽量都满足：

1. 一段提示词就能把目标、数据源、命令、输出格式写死，跑的过程中不需要只有主会话才有的项目上下文判断。
2. 机械、高 token：反汇编扫描、符号 / 字符串 / 资源批量提取、大文件或多目录探索、固定数据抽取、覆盖度梳理。
3. 产物能拿源头（二进制、代码、资源、原始日志）独立抽查。不能验证就不外包。
4. 产物是事实或素材，不直接改产品代码或项目状态。

命中任一就自己做：需要设计 / 架构 / 取舍判断；要改产品代码、跑构建、动数据库或远程状态；不可逆或对外的操作；产物无法验证。

简单说：外包「查事实、提素材」，不外包「做决定、改东西」。

## 2. 写交接提示词

按 `references/handoff-prompt-template.md` 填，以下七项缺一不可：

1. 让外包先读 `AGENTS.md` 和相关 skill（如项目启用的 `reverse-engineering`），遵守本项目红线。
2. 要拿的要点逐条列死，不写「大概」「酌情」。
3. 精确的数据源路径、目标（类 / 符号 / 文件）和可直接复制的命令。
4. 主会话已确定的结论，标明「已完成，别重做」，避免重复劳动和矛盾结论。
5. 输出写到哪个文件、追加到哪份文档哪一节、什么结构；每项标来源（文件路径 / 符号 / 地址 / 章节）。
6. 来源受限、跨环境或间接推断的结论，标来源和「需在目标环境确认」，不能写成已证实。
7. 信息不够下结论时，列出需要更深工具、真机或人工确认的具体项，不许编。

提示词默认存 `docs/handoffs/<slug>-PROMPT.md`；项目有领域目录（如 `reverse-engineering/<App>/`）时可以和领域产物放在一起。

## 3. 交给用户，然后停下

把提示词整段给用户，说清外包要产出哪个文件、写到哪、跑完后怎么回来。然后停下等用户，不要假装已经拿到结果。

## 4. 回收后必须验收

用户说「跑完了」后：

1. 读产物文档和结构化数据。
2. 挑最关键、最会驱动实现的几条声明（公式、常量、默认值、映射、地址、端点值），重新跑源头命令、重新 grep 或重新计算，逐条对照。只读文档觉得对不算验收。
3. 报账：✅ 通过 N 条 / ❌ 错误 M 条，错误的给出源头真值。
4. 有真值就直接改正产物，在报账里写清改了什么、依据哪条源头证据。
5. 外包自己标了中 / 低置信度并列入待确认的项，算诚实留白，不算错。

**不经抽查不得采信**，哪怕整体看着可信。实际常见的错误有操作数标反、常量抄错、端点值写反。

## 5. 记档

任务有档案（task-dossier）时，在台账记一条：外包了什么、给谁跑、产出哪些文件、抽查了几条、通过和纠错各几条、改了什么；续接启动词里带上「外包产物已验收」的状态。

项目启用了 reverse-engineering / benchmark-dev 时，外包产物同样要满足它们「一切可追溯」的要求。
