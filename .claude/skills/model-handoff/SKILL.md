# 模型间任务交接 Skill（主会话 agent ⇄ 外包 agent）

## 解决的问题

有些活**范畴死板、体量大、烧 token**：逆向反汇编扫描、`nm`/`strings` 批量符号提取、跨大文件探索、固定数据抽取、文档覆盖度爬梳。这类活不需要主会话 agent 的项目上下文判断，用一段界定清楚的提示词就能让 **外包 agent（默认 Grok）** 代跑，把主会话 token 省给真正需要判断的开发环节。本 skill 把「主会话定范畴 → 外包代跑 → 回灌文档 → 主会话验收续接」固化成协议。

默认角色假设：

| 角色 | 默认 | 可替换 |
|------|------|--------|
| **主会话 agent** | 当前对话里的 agent（Claude / Codex / Grok 等） | 任何负责设计与验收的会话 |
| **外包 agent** | Grok | 用户指定的另一模型会话 |

下文「主会话 / 外包」即指这两侧，不绑死产品名。

## 现实约束（务必先认清）

**主会话 agent 不能直接调用外包 agent。** 这是人在环（human-in-the-loop）交接，不是自动化桥接：

```
主会话判定+写提示词  →  用户把提示词丢进外包会话跑  →  外包把结果写进仓库文件
                                                              ↓
主会话继续开发  ←  主会话强制验收（拉回源头抽查）  ←  用户说「跑完了」
```

不得设计/暗示「主会话自动喊外包模型」的流程；主会话的职责是**产出可直接复制的提示词** + **回收后强制验证**。

## 一、适配闸门（Fitness gate）——先判断该不该外包

任何考虑外包的任务，先过闸门，输出一句裁决（`✅ 适合外包 / ❌ 自己做`）+ 理由。

**✅ 适合外包（四条尽量都满足）：**
1. **范畴可被一段提示词完全界定**——目标、数据源、命令、输出格式都能写死，外包跑的过程中不需要临场做「只有主会话手里项目上下文才能做」的判断。
2. **机械 / 高 token**——反汇编大扫描、符号/字符串/资源批量提取、大文件或多目录探索、固定数据抽取、覆盖度爬梳。
3. **产物可独立抽查**——输出是文档 / 结构化数据，主会话事后能拿源头（二进制、代码、资源、原始日志）交叉核对。**不可验证 = 不外包。**
4. **低耦合**——产物是「素材/事实」，不直接改动产品代码或项目状态。

**❌ 不外包（命中任一即自己做）：**
- 需要项目上下文的**设计 / 架构 / 取舍判断**；
- 直接改产品代码、跑构建、动数据库/远程状态等**项目状态**；
- **不可逆**或对外操作；
- 产物**无法被主会话验证**（没有可对照的源头）。

> 判据速记：外包「查明事实/提取素材」，不外包「做决定/改东西」。

## 二、生成交接提示词

用 `references/handoff-prompt-template.md` 的骨架填。**必含要素**（缺一不可）：

1. **协议引导**——让外包 agent 先读 `AGENTS.md` + 相关 skill（如逆向任务读 `reverse-engineering`，若项目启用了该 skill），遵守本项目红线。
2. **精确范畴**——要拿的要点/清单逐条列死，不留「大概、酌情」。
3. **数据源 + 可跑命令/配方**——精确路径、目标类/符号/文件、可复制命令或脚本思路，能抄就给全。
4. **「已完成，别重做」**——把主会话侧已钉死的结论列出来，防止重复劳动 + 制造矛盾。
5. **输出格式**——结构化写到**指定路径** + 追加到指定文档章节 + 汇总表；每项**标来源**（文件路径、符号、地址、章节等，按任务类型写清格式）。
6. **置信度 / 受限环境标注规则**——源受限、跨环境、合成环境或间接推断的结论，必须标来源 +「需在目标环境确认」，不得当已证实事实。
7. **升级而非瞎猜**——现有信息不足以定论的，要求**列出待更深工具/真机/人工确认的具体项**，不许编。

提示词存放：

- **默认**：`docs/handoffs/<slug>-PROMPT.md`
- **若项目有领域目录**（如 `reverse-engineering/<App>/`）：可放在该目录下的 `*-PROMPT.md`，与领域产物同处

## 三、交接（停，等用户）

把提示词整段贴给用户复制，并**明确告知**：外包该产出哪个文件、写到哪、跑完怎么回来。然后**停下**——这是人在环的手动步骤，不要假装已经拿到结果。

## 四、回收 + 强制验收（核心红线，不可跳过）

用户说「跑完了/你审核」后：

1. **读**产物文档 + 结构化数据。
2. **拉回源头抽查**——**不是「读文档觉得对」，是重跑源头对拆**：
   - 挑**最要命 / 最可落地**的若干条声明（会驱动实现的公式、常量、默认值、映射）；
   - 重新跑源头命令/重 grep/重算，与外包结论逐条对拆；
   - 地址、常量、分段公式、端点值、关键字段都要亲自复核。
3. **报账**——列「✅ 通过 N 条 / ❌ 实错 M 条」，实错给出**源头真值**。
4. **就地纠错**——有真值在手，直接改正产物文档 + 结构化数据（走 protocol-dev：小改可径改，但要在报账里讲清改了什么、依据哪条源头证据）。
5. **诚实留白 ≠ 错**——外包标了 medium/low 置信并挂进「待更深确认」的项，是诚实处理，认可即可，别当错算。

> 铁律：**绝不盖章放行**。哪怕外包整体可信，也必须实抽几条；实战里常见操作数标反、常量抄错、端点值写反。验收关卡就是防这个。

## 五、记档

外包是一条可追溯事件，写进 task-dossier 台账（若该任务有档案）：

- 外包了什么范畴、给谁跑；
- 产出了哪些文件；
- 验收抽查了哪几条、通过/纠错各几条、改了什么。

## 与其他 skill 的关系

- **task-dossier**：每次外包 = 一条台账事件；跨会话时续接启动词要带上「外包产物已验收」的状态。
- **reverse-engineering / benchmark-dev**（若项目启用）：外包产物必须满足同样的「一切可追溯」铁律 → 所以第四步验收是**强制**，不是「审一下」。
- **protocol-dev**：写提示词可自主；但「决定外包」先给裁决+提示词等用户跑（先谋后动），「回收结果」先验证再采信。

## 触发条件

- **自动（模式1）**：主会话规划/拆解任务时，某子任务命中适配闸门画像（逆向反汇编、批量提取、大范围探索、固定抽取），主动过闸门并建议外包 + 生成提示词，由用户决定是否真的去外包会话跑。
- **手动（模式2）**：用户说「交给 Grok」「外包给 Grok」「这个能不能让 Grok 做」「查画布式地探一下」等，或 `/model-handoff`。
