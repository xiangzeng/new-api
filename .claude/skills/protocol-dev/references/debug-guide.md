# Bug 调试规范

结论来自日志证据，不靠猜；每次改代码前都要用户批准。本项目的日志写法、日志位置和查看方式见 project-guide「调试」，下面的示例是通用写法。

多层 / 前后端 / 多进程项目，先判断问题在哪一层，必要时在跨层调用两端都打日志，分清是调用方还是被调方的问题。

## 1. 分析现象

说清：实际发生了什么、按设计应该发生什么、涉及哪些模块和执行路径、可能的触发条件。

## 2. 给调试方案，等批准

方案写在对话里，不写进代码：

- 对问题的理解和初步判断
- 在哪些文件、哪些位置加日志，为什么加在这里
- 日志设计：统一前缀（如 `📖 [模块名]`）便于过滤；要记录的变量、状态和分支判断结果
- 最后一句：「确认后我开始添加调试代码」

日志要覆盖：函数入口和出口、每个关键分支（能看出走了哪条）、异步操作的开始和回调、状态修改前后的值、跨层调用的请求和响应。

## 3. 加日志（批准后）

用项目语言写，形如：

```
log("📖 [模块.方法] 开始 - 入参=..., 关键状态=...")
log("📖 [模块] 进入 A 分支 - ...")    log("📖 [模块] 跳过 - 原因: ...")
log("📖 [边界] 请求 - ...")           log("📖 [边界] 响应 - ...")
```

程序用某个流（如 stdout）传输结构化数据（JSON-RPC 等协议流）时，调试日志写到另一个流（如 stderr），不要污染数据通道。

## 4. 看日志定根因

请用户复现并贴出完整日志。对比实际路径和预期路径，找到第一个异常点，基于日志给出根因。日志不够就再出一轮补充方案，不连续尝试「改一下试试」。

## 5. 修复与清理

1. 给修复方案（根因、思路、要改的代码），等确认。
2. 修复时保留调试日志，不顺手清理。
3. 请用户验证。
4. 确认修好后，问是否清理调试日志；用户同意才删，要求保留就不删。
