# 开发协议

> 本文件是通用件，所有项目一字不差，由模板仓库统一同步，不在项目里改。项目专属的规则写在 `AGENTS.md` 和 `references/project-guide.md`，与本文件冲突时以项目为准。

## 先给方案，等授权再动手

- 任何代码改动，不论大小，都先给方案，用户明确授权后再改文件。讨论阶段可以用伪代码或片段解释思路，但不改源文件。
- 授权词：改代码 —「执行」「开始开发」「写入代码」「改吧」「做吧」「就用方案 A」；改文档 —「写入文档」「更新文档」「写入 summary」「记录到文档」。
- 不需要方案、直接做的：回答技术问题、解释代码、生成 commit 信息。

## 按任务先读 reference

`references/project-guide.md` 是本项目对下面所有任务的补充（版本底线、构建验证、调试入口、提交与合并的特殊要求、项目流程、踩过的坑）。做任何一类任务前，先看它有没有相关小节，有就一并读，冲突时以它为准。

- 写代码、给代码方案、构建验证 → `references/project-guide.md`
- 生成 commit 信息 → `references/commit-guide.md`
- 分支合并 → `references/merge-guide.md` + `references/commit-guide.md`
- Bug 调试 → `references/debug-guide.md`
- 版本发布、部署 → project-guide「项目专属流程」里登记的文件（如 `references/release-guide.md`）；没有登记就先问用户

## 代码修改

1. 复述需求，有歧义先问。
2. 给方案：简单改动写清改哪个文件、哪个位置、改成什么；复杂功能给至少两个方案并比较优劣。用到较新的 API 时说明是否兼容项目的最低版本。
3. 等授权。用户否定或追问就调整方案，直到确认。
4. 按确认的方案实现，再按「构建与验证」验证，最后列出改了哪些文件。

## 版本兼容

- 所有 API 兼容项目的最低版本（见 project-guide），不假设用户环境是最新版本。
- 必须用更高版本 API 时，先告诉用户，并加可用性检查（`@available` / `if #available` / 特性检测 / 版本判断）或 polyfill，给出低版本的降级实现。
- 核心功能必须在最低版本可用；锦上添花的功能可以只在高版本提供，但要说明所需版本和低版本的表现。

## 文档更新

先在回复里展示要写入的内容，用户确认后再写文件。

## Commit 与 push

**`git commit` 流程**：读 commit-guide 生成信息并展示，主动问「确认无误，是否执行提交？」，用户确认后再提交。提交内容与展示的完全一致，不加 Co-Authored-By 等 AI 署名。

**`git push` 流程**：用户只说「提交」时只 commit；明确说「推送」「推 main」「部署」等时，commit 后直接 push，不再二次确认。强推（`--force` / `-f`）先说明风险、等确认。项目另有更严格的推送约束（如禁止直推 master、推送前需用户测试）时，以项目为准。

## 构建与验证

1. 按 project-guide「构建与验证」的命令和运行策略验证。
2. 签名、依赖缺失、环境不可用等环境问题不当作代码错误处理，记下关键报错并说明要在哪里解决。
3. 用户说「不 build」「只改代码」时，本轮不构建也不运行。

## 输出格式

- 不用 Markdown 表格（部分终端不渲染），对比信息用列表或「加粗标题 + 列表」分组。
- 方案里的文件清单分「新增文件」「修改文件」两组，每项写从项目根开始的完整路径和一句说明。
- project-guide 写了新文件需要登记的位置（如 Xcode target、路由表）时，方案里注明，执行后提醒用户完成登记。
